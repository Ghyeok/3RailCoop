# DECISION — 결정 기록

애매한 요구사항에 대해 사용자가 AI와 대화하며 직접 내린 결정을 기록한다. 기록 규칙은 `AGENTS.md`의 'DECISION 기록'을 따른다.

- 사용자가 직접 결정한 것만 기록한다. AI의 가정은 기록하지 않는다.
- 기존 항목은 수정하지 않는다. 결정이 바뀌면 새 항목을 추가하고, 이전 항목의 상태를 `D-xxx로 대체됨` 또는 `D-xxx로 부분 대체됨 (대체된 범위)`로만 표시한다.

항목 형식:

```
## D-xxx 제목
- 날짜 / 상태: 유효 | D-yyy로 대체됨 | D-yyy로 부분 대체됨 (범위)
- 맥락: 무엇이 애매했나
- 선택지: 검토한 안
- 결정:
- 얻은 것:
- 버린 것:
- 트레이드오프:
- 관련: SPEC 항목, 기획 섹션
```

---

## 미결 사항

아직 결정되지 않은 항목이다. 결정되면 `→ D-xxx`로 표시한다. 순서는 논의를 위한 제안이다. (출처: Game_Design.md §10, 2026.10.29 기준)

- **O-01 쿨타임과 판정 주기:** 이동 및 분리 직후 쿨타임의 구체적인 시간과 입력을 검사하는 시점. (관련: S-102, S-201, S-202)
- **O-02 인게임 표시:** 사망·암살 횟수와 스테이지 진행 바의 세부 배치. (관련: S-601, S-602) → D-015
- **O-03 장애물과 패턴:** 스테이지별 난이도 구성, 구체적인 등장 주기와 난이도별 조정, 전진 속도 수치, 회피 가능한 시간 및 충돌 판정. (관련: S-302, S-501, S-502) → 스테이지 구성 방식(패턴 개수·난이도 비율)은 D-012. 등장 주기·속도의 최종값과 난이도별 조정은 미정.
- **O-04 네트워크 입력 판정:** 틱 길이와 전송 여유 시간의 값, 공통 틱 시간 동기화의 구현 방법, 한 틱의 복수 입력 선택 및 재배정 입력의 쿨타임 검사 시점. 지연에 따른 재배정·폐기 정책은 Game_Design §4에 기록한 기준을 적용하고 플레이 테스트 후 조정한다. (관련: S-201, S-402)
- **O-05 암살 판정:** 다음 주기에 상대의 이동과 사망이 함께 판정되는 경우 등 세부 판정 기준. (관련: S-202, S-601, S-602) → 실시간 판정 기준은 D-015. 틱 판정(S-202)의 세부 기준은 미정.
- **O-06 MVP 테스트 스테이지:** 구체적인 장애물 구성과 검증 방법. (관련: S-302) → D-008
- **O-07 배경과 챕터:** 후보 배경과 지하철 통일 방향의 관계 및 챕터 구성.
- **O-08 상세 UI와 네트워크:** 캐릭터·이름·챕터 선택 UI, 결과·게임 오버 화면 구성, 연결 종료 시 화면, 지연에 따른 판정. (관련: S-702)
- **O-09 Antigravity 검수에서 나온 미승인 제안:** 판정 주기 0.1초, 이동·분리 직후 쿨타임 1틱, 쿨타임 검사 시점과 같은 주기의 분리·이동·충돌 처리 순서는 검토 제안일 뿐 확정값이 아니다. 같은 주기 입력을 모두 반영한 뒤 결과를 판정한다는 기존 규칙은 보존하며, 상세 이벤트 순서는 별도 합의 전까지 미정으로 둔다. (관련: S-201, S-202)
- **O-10 장애물 풀링 전환:** 전진 속도가 빨라지거나 사이클 간격이 짧아져 장애물 생성·삭제가 늘면 Destroy가 병목이 될 수 있다. 풀링으로 바꿀 기준(측정 방법, 생성 빈도·프레임 비용)과 시점은 미정. (관련: S-305, S-501, D-014)

## D-001 문서 체계를 AGENTS·SPEC·DECISION·HANDOFF로 재편

- 날짜 / 상태: 2026-11-23 / 유효
- 맥락: 기획, 진행 현황, 미결 사항, 인수인계 기준이 `Game_Design.md`와 여러 가이드에 흩어져 있어 세션이 초기화되면 맥락을 이어가기 어려웠다.
- 선택지: (a) 기존 문서 구조 유지 (b) 역할별 4개 문서로 재편하고 겹치는 내용을 옮김
- 결정: (b).
  - `AGENTS.md`는 루트에, `SPEC.md`·`DECISION.md`·`HANDOFF.md`는 `Docs/`에 둔다.
  - `Game_Design.md` §8(마일스톤·TODO·테스트 시나리오)과 §9 'MVP 테스트 순서'는 SPEC으로, §10(함께 결정할 사항)은 DECISION 미결 사항으로 옮기고 원래 자리에는 안내 한 줄만 남긴다.
  - `Context_Compaction_Guide.md`는 AGENTS(컨텍스트 관리·세션 시작 절차)와 HANDOFF(템플릿)로 나눠 옮긴 뒤 삭제한다.
  - `Style.md`와 `Model_Selection_Guide.md`는 내용을 옮기지 않고 삭제하며, AGENTS의 관련 규칙도 삭제한다.
  - 레포 문서를 기준으로 하고 Notion 원본 기획서는 갱신하지 않는다.
  - `Game_Design.md`의 확정 규칙은 소급해 DECISION으로 옮기지 않고, DECISION은 이 결정부터 기록한다.
- 얻은 것: 관심사마다 기준 문서가 하나로 정해지고, 세션 시작 시 HANDOFF만 읽으면 작업을 이어갈 수 있다.
- 버린 것: 명문화된 코드 스타일·명명 규칙(`Style.md`), 모델 선택 가이드, Notion 기획서와의 동기화, 과거 결정의 소급 기록.
- 트레이드오프: 항목마다 HANDOFF·SPEC 갱신 비용이 생긴다. 코드 스타일 일관성은 문서 없이 기존 코드에 맞춰야 한다. Notion 기획서는 점점 레포와 달라진다.
- 관련: 전체 문서

## D-002 SPEC 항목은 AI가 구현하고, 사용자 승인 후 체크

- 날짜 / 상태: 2026-11-23 / D-006로 부분 대체됨 (커밋·push·PR 부분)
- 맥락: 기존 규칙은 "코드는 사용자가 직접 작성하고, 요청할 때만 AI가 구현"이었다. SPEC 파이프라인(완료 기준 → 구현 → 자동 테스트 → 회귀 테스트 → 결과 보고)을 누가 수행하는지 정해야 했다.
- 선택지: (a) 기존 규칙 유지 (b) SPEC 항목은 AI가 끝까지 구현 (c) 항목마다 담당자 지정
- 결정: (b).
  - AI는 한 번에 한 항목만 진행하고, 다음 항목은 제안만 한 뒤 사용자 지시로 착수한다.
  - SPEC에 없는 작업은 요청이 있을 때만 하며, AI가 필요하다고 판단하면 SPEC 항목 추가를 제안한다.
  - AI가 결과를 보고하고 사용자가 승인한 뒤에만 체크한다.
  - `spec/S-xxx` 브랜치에서 작업하고, 승인을 커밋 허가로 본다. push·PR은 요청 시에만 한다.
- 얻은 것: 구현 속도, 항목 단위로 일관된 검증 절차.
- 버린 것: 사용자가 직접 코드를 작성하며 얻는 이해도와 통제감, 기존 "사용자가 직접 작성" 규칙.
- 트레이드오프: 사용자는 코드 작성 대신 결과 보고 검토와 승인에 시간을 쓴다. AI가 스스로 통과를 판정하는 위험은 승인 절차로 막는다.
- 관련: AGENTS.md '작업 범위'·'SPEC 진행 절차'·'Git'

## D-003 기존 구현은 검증 전으로, 미승인 계획은 `후보`로 등록

- 날짜 / 상태: 2026-11-23 / 유효
- 맥락: 이미 작성된 코드(이동, 장애물, Steam 로비 등)와 사용자 승인 전인 Antigravity 개발 계획안(Game_Design §8-1)을 SPEC에 어떻게 넣을지 정해야 했다.
- 선택지: (a) 기존 구현은 완료로 보고, 계획안은 그대로 착수 가능 상태로 등록 (b) 기존 구현은 검증 항목으로, 계획안은 `후보` 상태로 등록
- 결정: (b). 기존 구현은 "기존 구현 검증" 항목으로 등록해 파이프라인을 통과해야 완료로 본다. 계획안 항목과 AI가 작성한 완료 기준은 `후보`로 두고, 사용자가 완료 기준을 승인하면 `대기`로 바꾼다.
- 얻은 것: 검증되지 않은 코드와 승인되지 않은 계획이 완료나 확정으로 섞이지 않는다.
- 버린 것: 기존 작업을 곧바로 진척으로 인정하는 것.
- 트레이드오프: 착수 전에 완료 기준 승인과 기존 코드 검증이라는 단계가 더해진다.
- 관련: SPEC 전체

## D-004 테스트 정책

- 날짜 / 상태: 2026-11-23 / 유효
- 맥락: 프로젝트에 asmdef와 테스트 코드가 없고, Steam·2인 네트워크 기능은 자동화가 어렵다. '자동 테스트'와 '회귀 테스트'의 정의가 필요했다.
- 선택지: 모든 항목에 자동 테스트 의무 / 자동화 불가 항목은 수동 허용 / 테스트 정책 없이 항목마다 판단
- 결정:
  - 테스트 기반 구축(asmdef 분리, EditMode·PlayMode 테스트 어셈블리)을 S-000으로 가장 먼저 한다.
  - 규칙 로직은 MonoBehaviour와 분리된 순수 C#으로 작성하고 EditMode 테스트를 의무로 한다. PlayMode는 씬 통합이 필요할 때만 쓴다.
  - 자동화할 수 없는 항목만 `[수동]` 태그와 수동 검증 절차를 허용하고, 사용자가 수행한다.
  - 회귀 테스트는 항목마다 전체 자동 스위트를 Unity CLI로 실행하고, 수동 절차는 마일스톤이 끝날 때 다시 수행한다.
- 얻은 것: 핵심 규칙(틱, 합체·분리, 입력 재배정)을 빠르고 반복 가능하게 검증한다.
- 버린 것: 로직을 MonoBehaviour 안에 바로 작성하는 자유, 네트워크 기능의 완전 자동 검증.
- 트레이드오프: 로직 분리를 위한 설계 비용이 생긴다. 수동 항목은 마일스톤 사이에 회귀가 생겨도 늦게 발견될 수 있다.
- 관련: S-000, AGENTS.md '테스트 정책'

## D-006 커밋 이후 main 병합 절차

- 날짜 / 상태: 2026-11-23 / 유효 (D-002의 커밋·push·PR 부분을 대체)
- 맥락: 커밋 이후 main까지 가는 절차가 정해져 있지 않았다. main 직접 커밋과 PR 병합이 섞여 있었고, CodeRabbit은 연결되어 있지만 리뷰 대기가 병목이었다.
- 선택지:
  - 경로: (a) PR 경유 (b) 로컬 병합
  - 리뷰: (a) CodeRabbit (b) Claude Code 내부 리뷰(`/code-review high`)
  - 병합 방식: (a) squash (b) merge commit (c) rebase
- 결정:
  - PR 경유, 리뷰는 Claude Code 내부 리뷰. CodeRabbit 자동 리뷰는 `.coderabbit.yaml`로 끈다.
  - main 직접 커밋 금지(브랜치 보호 없이 AGENTS 규칙으로 운영). 브랜치는 최신 main에서 분기: `spec/S-xxx`, `chore/<주제>`(SPEC과 같은 검증), `docs/<주제>`(테스트·리뷰 생략).
  - 코드 리뷰는 결과 보고 전에 한다. 이번 변경이 만든 버그는 수정 후 테스트 재실행(재리뷰 1회까지), 기존 버그는 SPEC 항목 추가 제안, 사소한 지적은 범위 안이면 수정.
  - 사용자 승인 한 번으로 커밋 → push → PR → SPEC 체크·HANDOFF 갱신 커밋 → squash 병합 → 브랜치 삭제 → main pull까지 자동 진행.
  - PR 제목은 `S-xxx 제목`(또는 `docs:`/`chore:`), 본문은 결과 보고 내용.
  - 1회 예외(사용자 승인): 초기 구축 브랜치 `spec/S-000`은 문서 스캐폴드·pipeline 업그레이드·이 결정의 문서 반영을 `docs/`·`chore/`로 나누지 않고 PR 하나로 병합한다.
- 얻은 것: 리뷰 대기 병목 제거, 승인 한 번으로 main 반영, SPEC 항목 하나가 main 커밋 하나로 대응.
- 버린 것: 외부 리뷰어(CodeRabbit)의 독립적인 시각, 브랜치 내부 중간 커밋의 main 이력, 브랜치 보호에 의한 강제.
- 트레이드오프: 같은 모델 계열이 구현과 리뷰를 모두 해서 맹점이 겹칠 수 있다. 승인 후 병합까지 자동이라 승인 시점의 검토가 유일한 사람의 관문이다.
- 관련: AGENTS.md 'SPEC 진행 절차'·'Git', D-002

## D-007 MVP를 로컬 1인·실시간 판정으로 재정의

- 날짜 / 상태: 2026-11-23 / 유효
- 맥락: 기존 MVP 완료 기준은 한 기기 확인 뒤 Steam 친구와 온라인 2인 테스트까지 포함했고, 틱 판정 구조(S-201)를 먼저 설계하는 순서였다. S-201은 논의가 많이 필요해 보류됐고, MVP를 빠르게 완성하는 것을 목표로 범위를 다시 정해야 했다.
- 선택지:
  - 범위: 온라인 포함 / 로컬 1인
  - 판정: 틱 구조 먼저 / 실시간 판정
  - 포함 기능: 합체·분리, 이동 쿨타임, 클리어, 사망·암살 기록 UI 중 선택
- 결정:
  - MVP는 1명의 로컬 플레이어가 Steam과 관계없이 두 플레이어를 조작해 짧은 테스트 스테이지를 진행하고, 게임 오버·재시도·클리어까지 할 수 있는 상태로 한다.
  - 포함: 이동 쿨타임, 합체·분리, 클리어(목표 거리). 제외: 사망·암살 기록 UI.
  - 판정은 틱 없이 실시간으로 한다. 규칙 로직은 순수 C#으로 작성해 네트워크 단계에서 재사용한다.
  - Steam 검증 항목(S-401·S-701)과 네트워크·틱 항목은 MVP 이후로 미룬다.
  - MVP 항목: S-101 → S-301 → S-103 → S-203 → S-302 → S-304.
- 얻은 것: 틱 판정 논의 없이 핵심 재미(이동·합체·분리·회피)를 빠르게 플레이해 볼 수 있다.
- 버린 것: 처음부터 틱 구조로 판정해 네트워크 단계에서 판정 코드를 재사용하는 것(기존 진행 순서 원칙), MVP 안에서의 온라인 조작감 검증.
- 트레이드오프: 네트워크 단계에서 판정 시점을 틱 구조(S-201·S-102·S-202)로 다시 작성해야 한다. 실시간 판정에서 확인한 조작감이 틱 판정에서는 달라질 수 있다.
- 관련: SPEC 'MVP 목표와 진행 순서', S-103, S-203, S-302, S-304, Game_Design §8(기존 MVP 기준)

## D-008 MVP 테스트 스테이지 구성

- 날짜 / 상태: 2026-11-23 / 유효
- 맥락: MVP 전체 플레이(S-304)에 쓸 짧은 테스트 스테이지의 패턴 구성, 목표 거리, 전진 속도, 장애물 간격이 정해지지 않았다(O-06). 이동 쿨타임 기본값과 재시도 키도 MVP 구현에 필요했다.

- 관련: S-304, O-06, O-01, O-03, Game_Design §5

## D-009 장애물 패턴 설정 오류는 유효한 패턴으로 무작위 대체

- 날짜 / 상태: 2026-11-25 / 유효
- 맥락: 스포너의 패턴 목록에 빈 참조나 유효하지 않은 사이클이 있으면 장애물 없이 스테이지가 진행되어 클리어될 수 있었다(S-304 리뷰 pre_existing). S-303 후보 기준은 스테이지를 시작하지 않고 설정 오류를 표시하는 것이었다.
- 선택지:
  - 오류 처리: 스테이지 미시작·오류 표시 / 유효한 패턴으로 무작위 대체
  - 대체 후보: 빈 패턴 포함 / 장애물이 있는 패턴만
  - 선택 시점: 시도마다 새로 / 스테이지 시작 때 고정
  - 대체 불가(유효한 패턴 없음, 프리팹·전진 기준 누락): 장애물 없이 진행 / 미시작·오류 표시
- 결정:
  - 사람의 실수로 패턴이 잘못 입력되어도 게임이 멈추면 안 된다. 잘못된 패턴은 같은 목록의 유효한 패턴 중 하나로 무작위 대체하고, 설정 오류 로그를 남긴다.
  - 대체 후보는 장애물이 하나 이상 있는 유효한 패턴만이다(빈 패턴 제외).
  - 재시도할 때마다 새로 고른다.
  - 대체할 수 없으면 오류 로그를 남기고 장애물 없이 진행한다.
- 얻은 것: 설정 실수가 있어도 플레이가 멈추지 않고, 잘못된 자리에도 장애물이 나온다.
- 버린 것: 설정 오류를 화면에 띄워 즉시 알아차리는 것(S-303 후보 기준).
- 트레이드오프: 오류는 로그로만 드러나므로 개발 중 로그를 확인해야 한다. 대체 패턴의 길이가 원래와 다르면 스테이지 길이와 목표 거리가 맞지 않을 수 있다. 무작위 선택은 네트워크 단계(S-501·S-402)에서 호스트·게스트가 같은 결과를 보도록 동기화해야 한다.
- 관련: S-303, S-304, S-501, Game_Design §5

## D-010 Steam 미실행 시 자동 실행, 로비 실패는 오류 팝업으로 안내

- 날짜 / 상태: 2026-11-25 / 유효
- 맥락: S-401 수동 검증 중, Steam 클라이언트를 켜지 않고 Create Room을 누르면 반응이 없고, 게임 실행 뒤 Steam을 켜도 계속 반응이 없었다. Steam 초기화를 게임 시작 때 한 번만 시도하기 때문이다. Steam 오프라인, 로비 생성·참가 실패와 시간 초과도 로그만 남고 화면 안내가 없다.
- 선택지:
  - Steam 미실행 처리: 안내 팝업 + Steam 실행 버튼 / 버튼을 누르면 자동 실행 / 안내 팝업만
  - 안내 범위: 로비 실패 전체 / Steam 미실행만
  - Steam 준비 후: 방 만들기 자동 진행 / 버튼을 다시 누름
- 결정:
  - Steam이 꺼져 있으면 Create Room을 누를 때 게임이 Steam 클라이언트를 자동으로 실행하고, Steam이 준비·로그인되면 게임을 다시 켜지 않고 방 만들기를 자동으로 이어간다.
  - Steam 준비 대기 시간은 30초. 넘으면 오류 팝업을 띄운다.
  - Steam 미설치·준비 시간 초과·오프라인·로비 생성 실패와 시간 초과·참가 실패와 시간 초과·NGO 연결 시간 초과를 모두 원인을 적은 오류 팝업으로 안내한다.
  - 팝업 문구는 영문(기존 인게임 메시지와 같음).
- 얻은 것: Steam을 켜는 것을 잊어도 버튼 한 번으로 이어지고, 실패 원인을 화면에서 바로 알 수 있다.
- 버린 것: 자동 실행 전에 사용자에게 묻는 단계. Steam 로그인 창이 뜨는 동안 상황 안내는 실행 중 상태 표시에 맡긴다.
- 트레이드오프: 개발 빌드에서는 `steam://` 실행을 쓰며, 출시 빌드의 `RestartAppIfNecessary` 처리는 따로 다뤄야 한다. Steam 로그인이 30초보다 오래 걸리면 오류 팝업이 뜬 뒤 다시 눌러야 한다.
- 관련: S-403, S-401, O-08, Game_Design §6

## D-011 SPEC 우선순위 3단계와 `수동 대기` 상태

- 날짜 / 상태: 2026-11-25 / 유효
- 맥락: MVP 이후 착수 순서가 한 줄 목록이고 우선순위 구분이 없었다. 남은 항목 대부분이 Steam·2PC 환경을 요구하는데, 사용자는 Steam 수동 검증의 우선순위를 낮게 보고 미루기로 했다. S-401은 [수동] 검증만 남아 `진행 중`에 묶여 있어 한 번에 한 항목 규칙 때문에 다른 항목을 시작할 수 없었다.
- 선택지:
  - 다음 목표: 로컬 플레이 다듬기 우선 / 온라인 2인 플레이 우선
  - 표기: 착수 순서 영역에서 높음·보통·낮음으로 묶기 / 항목마다 우선순위 필드 / 순서만 재정렬
  - 수동만 남은 항목: 자동 부분 병합 후 `수동 대기` 상태 / 브랜치에 계속 보관
  - 네트워크가 섞인 항목: 로컬·동기화 항목으로 분리 / 그대로 유지
- 결정:
  - 로컬 플레이를 먼저 다듬고, Steam·2PC가 필요한 항목은 환경이 준비되면 묶어서 진행한다.
  - SPEC '착수 순서' 영역에서 `높음`·`보통`·`낮음`으로 묶는다. 높음: S-502 → S-602. 보통: S-201 → S-102 → S-202. 낮음: S-401 [수동] → S-403 → S-701 → S-402 → S-501 → S-601 → S-702 → S-703 → S-704.
  - 새 상태 `수동 대기`: 자동 테스트·회귀·리뷰를 통과해 자동 부분을 병합하고 [수동] 결과만 남은 항목. 체크하지 않으며 진행 중으로 세지 않는다. 수동 결과가 오면 `보고됨` → 승인 → `완료`, 문제가 나오면 `진행 중`으로 돌린다.
  - S-501·S-601은 로컬 부분을 S-502·S-602(`후보`)로 나누고, 원래 항목에는 동기화 범위만 남긴다. S-502·S-602는 착수 전에 미결 사항(O-03, O-02·O-05)을 정하고 완료 기준을 승인받는다.
  - 틱 구조(S-201·S-102·S-202)는 네트워크 지연 처리용이라 로컬 항목 뒤 `보통`에 둔다. S-704는 맨 끝.
  - 로컬 콘텐츠 항목(난이도 2·3 스테이지, 챕터)은 S-502 뒤에 필요하면 제안한다. S-303 리뷰의 기존 버그(플레이 중 Inspector에서 패턴 변경 시 생성 중단)는 개발 중에만 생기는 경로라 항목으로 추가하지 않는다.
- 얻은 것: 2PC 환경 없이도 진행할 항목이 분명해지고, 수동 검증이 남은 항목이 다른 작업을 막지 않는다.
- 버린 것: 온라인 2인 플레이를 빨리 확인하는 것. 네트워크 지연과 조작감 확인이 늦어진다.
- 트레이드오프: 로컬 항목을 실시간 판정으로 먼저 만들면, 틱 구조(S-201) 도입 때 판정 시점(특히 암살 기준)을 다시 맞춰야 한다. `수동 대기` 항목이 쌓이면 2PC 검증 때 한꺼번에 문제가 드러날 수 있다.
- 관련: D-007, S-401, S-501, S-502, S-601, S-602, S-201, S-704, AGENTS.md 'SPEC 진행 절차'

## D-012 스테이지를 패턴 개수와 난이도별 비율로 무작위 구성

- 날짜 / 상태: 2026-11-25 / 유효
- 맥락: S-502(난이도별 무작위 패턴 선택)의 완료 기준에 필요한 스테이지 길이, 난이도 구성 방식, 등장 간격·속도(O-03), D-008 고정 테스트 스테이지와의 관계가 정해지지 않았다. 패턴 에셋은 난이도 1 핵심 패턴 4개뿐이고 난이도 값이 없다.
- 선택지:
  - 스테이지 길이: 패턴 개수 N개(목표 거리 자동) / 목표 거리 고정(닿을 때까지 패턴 선택)
  - 간격·속도: 현재 값 유지 / 새로 정함
  - D-008 고정 스테이지: 고정 순서·무작위 병행 / 무작위로 대체
  - 패턴 에셋: 난이도 1·2 전체 / 핵심 패턴만
  - 난이도 구성: 허용 난이도 중 같은 확률 / 허용 난이도별 비율
  - 비율 적용: N×비율의 정확한 개수 / 고를 때마다 비율을 확률로
  - 배치 순서: 전체 무작위 섞기 / 쉬운 난이도부터
  - 비율 설정 오류: 보정 후 진행 / 같은 확률로 대체
- 결정:
  - 스테이지 길이는 패턴 개수 N으로 정하고, 목표 거리(클리어 지점)는 마지막 장애물 직후로 자동 계산한다.
  - 전진 속도 5, 사이클 간격 1초, 시작과 패턴 사이 빈 사이클 3개는 D-008 값을 유지한다. 난이도별 간격·속도 조정은 미룬다(O-03).
  - 스테이지 설정에 고정 순서와 무작위 모드를 두어 D-008 고정 테스트 스테이지를 유지한다.
  - Game_Design §5의 난이도 1 패턴 10개와 난이도 2 패턴 5개를 에셋으로 만든다. 난이도 3은 설명과 숫자 표기가 맞지 않아 확인될 때까지 제외한다.
  - 스테이지에 허용 난이도와 난이도별 비율(%)을 정한다. 난이도별 패턴 개수는 N×비율로 정확히 맞춘다(예: N=10, 난이도 1 70%·난이도 2 30% → 7개·3개). 각 난이도 안에서 패턴은 무작위로 고르며, 같은 패턴이 반복되거나 연달아 나와도 된다.
  - 정해진 패턴들을 난이도와 관계없이 전체 무작위로 섞어 배치한다. 재시도할 때마다 새로 고르고 섞는다.
  - N×비율이 정수가 아니면 개수 합이 N이 되도록 나머지가 큰 난이도부터 1개씩 더한다. 비율 합이 100%가 아니면 비율대로 다시 계산하고 오류 로그를 남긴 뒤 진행한다(D-009와 같이 멈추지 않음).
- 얻은 것: 스테이지마다 난이도 구성을 비율로 조절할 수 있고, 같은 스테이지도 재시도마다 순서가 달라진다. 고정 테스트 스테이지로 기존 검증을 계속할 수 있다.
- 버린 것: 목표 거리를 직접 정하는 방식(무작위 모드), 쉬운 패턴부터 나오는 난이도 곡선, 난이도 3 패턴.
- 트레이드오프: 패턴마다 사이클 수가 달라 같은 N이라도 스테이지 길이가 시도마다 달라진다. 개수를 정확히 맞추므로 N이 작으면 비율이 그대로 표현되지 않는다(반올림 보정). 무작위 결과는 S-501에서 호스트·게스트가 같도록 동기화해야 한다.
- 관련: S-502, S-501, D-008, D-009, O-03, Game_Design §5

## D-013 비율을 준 난이도에 유효한 패턴이 없을 때의 보정

- 날짜 / 상태: 2026-11-25 / 유효
- 맥락: D-012에서 난이도별 개수를 N×비율로 정하기로 했지만, 비율을 준 난이도에 유효한 패턴이 하나도 없을 때의 처리가 정해지지 않았다. AI가 S-502 완료 기준에 가정으로 적은 처리를 사용자가 승인했다.
- 선택지: 그 개수를 남은 난이도에 비율대로 나눔 / 허용 난이도 전체에서 같은 확률로 고름 / 그 개수만큼 패턴을 빼고 진행
- 결정:
  - 그 난이도의 개수를 남은 난이도에 비율대로 나누고 오류 로그를 남긴 뒤 진행한다. 나눌 때 소수점은 D-012와 같이 나머지가 큰 난이도부터 1개씩 더해 합 N을 맞춘다.
  - 허용 난이도 전체에 유효한 패턴이 없으면 D-009와 같이 오류 로그를 남기고 장애물 없이 진행한다.
- 얻은 것: 패턴 에셋이 빠져도 스테이지 길이(N)와 나머지 난이도 구성이 유지되고 게임이 멈추지 않는다.
- 버린 것: 빠진 난이도를 같은 확률로 메우는 방식, 그 자리를 비워 스테이지를 짧게 하는 방식.
- 트레이드오프: 실제 난이도 구성이 설정한 비율과 달라지며, 로그를 확인해야 알 수 있다.
- 관련: S-502, D-012, D-009, Game_Design §5

## D-014 지나간 장애물은 Destroy로 정리하고 풀링 전환 여지를 둔다

- 날짜 / 상태: 2026-11-25 / 유효
- 맥락: S-502 수동 플레이에서 시야를 벗어난 장애물이 사라지지 않고 남는 현상이 발견됐다. 지금은 재시도 때만 장애물을 지운다. 정리 방식으로 Destroy와 오브젝트 풀링을 비교했다.
- 선택지: Destroy / 오브젝트 풀링
- 결정:
  - 플레이어보다 일정 거리 이상 뒤로 지나간 장애물은 Destroy로 정리한다.
  - 속도가 빨라져 장애물 수가 늘면 병목이 생길 수 있으므로, 생성과 삭제를 스포너의 한 곳으로 모아 나중에 풀링으로 바꿀 수 있게 둔다. 전환 기준은 미정(O-10).
- 얻은 것: 지금 규모(초당 생성 수 개)에서 단순한 구현, 재시도·네트워크 동기화(S-501) 방식이 정해지기 전에 풀링 구조를 미리 고정하지 않음.
- 버린 것: 처음부터 풀링을 적용해 생성·삭제 비용을 없애는 방식.
- 트레이드오프: 생성 빈도가 크게 늘면 GC·Instantiate 비용이 생길 수 있고, 그때 풀링으로 바꾸는 작업이 필요하다.
- 관련: S-305, O-10, S-501

## D-015 로컬 사망·암살 기록 기준과 인게임 상단 표시

- 날짜 / 상태: 2026-11-25 / 유효
- 맥락: S-602(사망·암살 기록 로컬) 착수 전에 표시 배치(O-02)와 암살 판정(O-05)이 정해지지 않았다. 기획의 암살 기준은 '분리 다음 판정 주기의 사망'인데 현재 판정은 실시간이고, 한 기기에서는 두 플레이어가 분리 키(Space) 하나를 함께 써 누가 분리했는지 구분할 수 없다. 합체 중 충돌 때 누구의 사망으로 셀지도 정해지지 않았다.
- 선택지:
  - 분리 키: 플레이어별 분리 키 / 공용 키 유지와 개별 키 추가 / 공용 키 유지, 암살 기록은 S-601에서
  - 실시간 암살 기준: 분리 후 N초 안의 사망 / 분리 후 상대의 다음 이동 전까지 / 분리 직후 쿨타임 안의 충돌만
  - 합체 중 사망: 닿은 플레이어 모두 / 먼저 닿은 한 명만
  - 표시 배치: 좌우 구석 기록과 상단 중앙 진행 바 / 상단 전체 진행 바와 그 아래 기록 / 상단 중앙 한 줄 묶음
- 결정:
  - 로컬(한 기기)은 공용 분리 키를 유지한다. 공용 키 입력은 두 플레이어의 동시 분리로 보므로 로컬에서는 암살이 기록되지 않는다. 암살 판정 로직과 테스트는 S-602에서 만들고, 플레이어별 입력이 생기는 S-601에서 실제 기록에 쓴다.
  - 실시간 암살 기준: 한 플레이어만 분리한 뒤 N초(Inspector 조절, 기본 0.5초) 안에 상대가 사망하면 분리한 플레이어의 암살 횟수를 올린다. 그 사이 상대가 직접 이동해 레일이 바뀌었으면 암살이 아니다. 쿨타임으로 무시된 이동 입력은 이동으로 보지 않는다. 같은 프레임에 두 플레이어가 모두 분리하면 암살이 아니다.
  - 게임 오버가 된 프레임에 장애물에 닿은 플레이어마다 사망 횟수를 올린다. 합체 중이면 두 플레이어 모두 올린다.
  - 인게임 상단 표시: P1 사망·암살은 왼쪽 위, P2는 오른쪽 위, 스테이지 진행 바는 상단 중앙. 진행 바는 매 프레임 부드럽게 올라간다.
- 얻은 것: 로컬 입력 구조(S-203)를 바꾸지 않고 사망 기록·UI를 먼저 다듬을 수 있다. 암살 판정 규칙은 테스트로 고정해 S-601에서 재사용한다.
- 버린 것: 로컬에서 플레이어별 분리 키로 암살을 바로 기록하는 방식.
- 트레이드오프: 로컬 플레이에서는 암살 횟수가 늘 0이라 암살 재미를 S-601 전까지 확인할 수 없다. N초 기준은 틱 판정이 생기면(S-202) 다시 맞춰야 할 수 있다.
- 관련: S-602, S-601, S-202, O-02, O-05, Game_Design §4 사망과 암살 기록, §6 인게임 UI
